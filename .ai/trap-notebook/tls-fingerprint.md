# TLS Fingerprint Trap Notebook: Historical Category Summary

Historical record of failures, fixes, and observations for ZeroProxy client-TLS (`rustls 0.23` + `rustls-rustcrypto` in WASM linear memory). **This document is not a currently approved specification.** All measurements reflect conditions at the time of recording, and no new runtime execution or verification was performed during this documentation pass. Previously proposed tests and implementation gaps are historical notes rather than current TODO items. Status documents such as `PHASE2_STATUS.md` and deleted `ARCHITECTURE`/`PHASE` files are historical references, not authoritative specifications.

Security invariant: **client-TLS must never leak to the server, and fingerprint mimicry must never bypass this boundary.** Early conclusions below claiming "wire work complete, IP is the sole cause" were refuted by subsequent wire inspections and session comparisons. Do not conflate distinct NAVER latency and rendering issues into a single root cause. In particular, the [July 28 correction](LOG.md#2026-07-28-2) retracted the `END_STREAM`/deflate withholding narrative in favor of a yamux lost wakeup bug; the July 3 GREASE/binder defects below are not the single root cause of all NAVER latency.

<a id="2026-07-03-naver-tarpit-root-cause-is_grease_value-bit-bug-extension-grease-wire-not-emitted-version-grease-encode-random-call-resumption-binder-decrypterror"></a>
## 2026-07-03: NAVER tarpit (GREASE predicate, compression list, and binder regression)

- **Cause (missing extension GREASE):** `ja3.rs::is_grease_value` restricted the upper nibble to `0xA`, recognizing only `0xaaaa` out of the 16 valid GREASE values. Most extension GREASE entries were dropped in the `msgs/macros.rs:227::encode_one` fast path, whereas cipher and group GREASE values bypassed that predicate and remained on the wire. Matching JA4 and Akamai hashes alone did not expose this wire discrepancy.
- **Fix (predicate and compression):** Replaced the predicate with `(v & 0x0f0f) == 0x0a0a && (v >> 8) == (v & 0x00ff)`. Because rustls pre-populated `Brotli+Zlib` and an `is_none()` guard prevented overriding it, `apply_chrome_ja3_shape` was updated to set `[Brotli]` unconditionally. Even if internal offered lists form a superset, the server wire selection is restricted to Brotli.
- **Separate regression (binder):** Calling `random_grease()` on every `SupportedProtocolVersions::encode` invocation caused PSK binder serialization to differ from the final wire serialization, triggering intermittent `DecryptError` failures on NAVER session resumption. Fixed version GREASE to `ProtocolVersion::Unknown(0x0a0a)`. **Never place RNG calls inside serialization paths that can be invoked multiple times.** If per-handshake random GREASE is required, generate it once per handshake and store it on the handshake struct.
- **Historical verification:** Observed matching Chrome `peetprint` hashes on `tls.peet.ws`, full NAVER document transfer, normal stream closure, and disappearance of the tarpit delay. Traces on `cologger.shopping.naver.com` had previously shown server-side delays, while direct Chrome on the same IP responded immediately, refuting the earlier IP-reputation diagnosis. Wikipedia, GitHub, and Cloudflare checks verified **TLS handshake completion only** and did not resolve all downstream GitHub or Cloudflare compatibility issues.
- **Unresolved separate issue:** Even when the kernel transferred and closed the full document, the browser DOM intermittently stalled at `interactive` as if truncated. Traces showed the initial `www.naver.com` document stream being canceled, refetched, and closed. Attributed at the time to an unconfirmed Service Worker `streamDocumentResponse`/`HtmlTxn` rendering path hypothesis.
- **Evidence:** `third_party-rustls-fork/src/ja3.rs`, `third_party-rustls-fork/src/msgs/macros.rs`, [client/hs.rs](../../third_party-rustls-fork/src/client/hs.rs). Specific bot-scoring heuristics remain historical interpretations; hash equality does not guarantee equivalence across all wire fields or WAF checks.

<a id="2026-06-02-phase-58-captured-spec-cipher-wire-emit-fork-header-order-ua-alignment-chrome-148-spec-baseline-update-ja3-cipher-tuple-byte-equivalent-chrome-148-8daaf6152771-nidnavercom-target_connect_failed-normal-load-restored"></a>
## 2026-06-02: Phase 5.8 (applying captured ciphers, header order, and UA on the wire)

- **Cause:** The captured spec in Phase 5.7 applied only to extension ordering while cipher suites still came directly from `config.provider.cipher_suites`. Chrome 134 grouped ciphers, SCSV, automatic padding, Firefox-style `record_size_limit`, and UA/TLS/`sec-ch-ua` version mismatches remained. Iteration via Service Worker `Headers.entries()` sorted wire headers alphabetically, forwarded opt-in client hints without an `Accept-CH` grant, and let the kernel append `user-agent` at the end.
- **TLS fix:** Updated [third_party-rustls-fork/src/client/hs.rs:392-410](../../third_party-rustls-fork/src/client/hs.rs) to emit captured cipher suites on the wire while retaining the provider cipher list for `ServerHello` validation. Omitted SCSV when using a captured spec and emitted padding only when present in the captured spec. Legacy RSA ciphers were advertised as decoys at the time, with modern servers selecting implemented TLS 1.3 ECDHE suites.
- **Baseline fix:** Updated the captured spec in [web/sw.js:495](../../web/sw.js#L495) to Chrome 148 cipher and extension ordering (excluding ECH; captured curves included MLKEM). Reordered fallback ciphers in [tls.rs:91-119](../../crates/zp-bundle/src/kernel/transport/tls.rs#L91-L119) to interleave ECDSA and RSA across AES128, AES256, and CHACHA. **Presence in captured curve lists does not imply actual support or wire emission;** the MLKEM revert in Appendix 1 below supersedes this note.
- **HTTP fix:** Updated [web/sw.js:636-708](../../web/sw.js) to drop ungranted `device-memory`, `downlink`, `dpr`, `ect`, `rtt`, high-entropy `sec-ch-ua`, and `viewport`/`save-data`/`prefers-*` hints, and enforced Chrome header ordering. Placed `user-agent` inline and removed the `user-agent` strip in [kernel/mod.rs:258](../../crates/zp-bundle/src/kernel/mod.rs#L258). Updated the fallback UA in [web/zp-core.js:22](../../web/zp-core.js#L22) to Chrome 148 while preferring the page's native UA.
- **Historical verification and limits:** On `tls.peet.ws`, the cipher tuple was byte-equivalent to Chrome 148, though full JA3/JA4 hashes still differed due to ECH and group/`key_share` differences. `nid.naver.com` recovered from `TARGET_CONNECT_FAILED` to load the login page, but the HTTP slow-lane persisted. The conclusion that "wire work is finished, only IP reputation remains" was premature without full wire verification, and attributing the delay solely to IP based on direct Chrome cold loads was later corrected by the session continuity comparison below.
- **Historical verification principle:** Distinguish installing a spec from emitting it on the wire, and verify the emission path for each field individually. Byte-level comparisons, golden tests, and end-of-phase fingerprint diffs were proposals at the time rather than completed CI checks. Related symbols: [apply_chrome_ja3_shape](../../third_party-rustls-fork/src/client/hs.rs), [chrome_ordered_cipher_suites](../../crates/zp-bundle/src/kernel/transport/tls.rs), [capturedFingerprint](../../web/sw.js), [HEADER_ORDER](../../web/sw.js), [UA strip removal](../../crates/zp-bundle/src/kernel/mod.rs#L258).

**Appendix 3: Missing HTTP/2 HEADERS PRIORITY flag and payload**

- **Cause:** Even when Akamai hashes matched, ZeroProxy `HEADERS` frames lacked Chrome's `PRIORITY` flag and 5-byte stream dependency payload. Because the Akamai hash covers only a subset of fields (`SETTINGS`, `WINDOW_UPDATE`, pseudo-headers), hash equality does not prove wire equivalence.
- **Fix:** Added `Headers::set_priority`, flag setters, and pre-HPACK dependency encoding in [headers.rs](../../third_party-h2-fork/src/frame/headers.rs). Configured root dependency, exclusive bit, and weight 256 (wire byte 255) in [client.rs](../../third_party-h2-fork/src/client.rs) with a getter in [priority.rs](../../third_party-h2-fork/src/frame/priority.rs), including the extra 5 bytes in frame payload length fix-ups.
- **Historical verification:** `HEADERS` flags and priority fields on `tls.peet.ws` matched Chrome 148, and Wikipedia, NAVER Mail, `nid`, and GitHub load checks passed. This superseded earlier notes proposing a future priority patch.

**Appendix 2: Discarding entire HTTP/2 responses on partial body error on GitHub**

- **Cause:** After a valid TLS/H2 handshake and response headers, the stream closed before reaching the declared `content-length`, raising `h2: body: bytes remaining on stream`. Immediate error propagation in [http2.rs:213-225](../../crates/zp-bundle/src/kernel/transport/http2.rs#L213-L225) discarded all previously received body bytes.
- **Historical workaround:** Preserved fatal error propagation when the received body was empty, but returned a partial response when bytes had already been received, logging `tx:h2-body-trunc bytes=N err=...`. This was a historical compatibility workaround rather than a general specification declaring truncated responses safe.
- **Historical verification and correction:** Observed cold-load completion on GitHub. While traces localized this failure to body stream handling, the broader claim that "any fingerprint issue must fail during the TLS/H2 handshake" does not hold in general, nor did this fix resolve all other GitHub or Cloudflare issues.

**Appendix 1: Advertising unimplemented MLKEM in `supported_groups` broke NAVER TLS (reverted)**

- **Cause:** Advertising unimplemented MLKEM via `exts.named_groups = Some(captured_groups)` passed `tls.peet.ws` via X25519 fallback, but `nid.naver.com` TLS failed immediately (hypothesized to be an MLKEM HelloRetryRequest for which no `key_share` generator existed).
- **Final fix and constraint:** Reverted the `supported_groups` override and documented the constraint in [hs.rs](../../third_party-rustls-fork/src/client/hs.rs). Actual advertised curves at that point remained `X25519`, `P-256`, and `P-384`, superseding earlier notes claiming MLKEM wire emission. Never advertise a group in `supported_groups` without a matching `key_share` implementation merely to match a fingerprint string.
- **Historical gap:** `rustls_rustcrypto` lacked an `X25519MLKEM768` key share generator at the time; notes referencing `pqcrypto-mlkem` or `rustls-post-quantum` and WASM size measurements were unimplemented proposals.

**Additional historical gaps and security notes**

- Re-enabling ECH using BoringSSL `ssl_grease_ech_seed` and `draft-ietf-tls-esni-22` with `mail.naver.com` regression checks was recorded as a future proposal, not completed work.
- Recorded a security gap where `/zp/api/diag/trace` could be fetched from arbitrary origins. **Diagnostic endpoints must not be exposed unprotected in production environments.** Gating via `ZP_CONTROL_TOKEN` or dev-only restrictions was proposed at the time without verification of deployment in this excerpt.
- Partial TLS or page-load successes recorded here do not close unresolved GitHub, Cloudflare, or CNN compatibility issues.

## 2026-06-02: Phase 5.7 (ECH GREASE broke `mail.naver.com` TLS handshake)

- **Cause and observation:** Following NAVER Mail links ended in `TARGET_CONNECT_FAILED`. Direct Schannel requests renegotiated and redirected normally, and disabling only ECH GREASE in ZeroProxy allowed the inbox to load. The payload at the time was an `EncryptedClientHelloOuter` extension with `HKDF_SHA256`/`AES_128_GCM` and random `config_id`, `enc`, and payload bytes.
- **Fix:** Removed the ECH GREASE block from `third_party-rustls-fork/src/client/hs.rs::apply_chrome_ja3_shape` while keeping padding. Claims that the server misparsed random ECH GREASE as real ECH or relied on BoringSSL's deterministic seed were **unverified server-side hypotheses**; only the disable-bisect result was empirically established.
- **Historical verification and limits:** Passing `www`, `nid`, Wikipedia, and GitHub did not guarantee `mail.naver.com` compatibility. Cross-subdomain regression checks were proposed at the time. Introduced in commit `7bec5bd`; see [hs.rs apply_chrome_ja3_shape](../../third_party-rustls-fork/src/client/hs.rs) and BoringSSL `ssl_grease_ech_seed` for historical context.

<a id="2026-06-02-update-60s-slow-lane-real-cause-ip-not-session-continuity"></a>
## 2026-06-02: UPDATE (`nid` cold slow-lane and session continuity)

- **Subsequent observation:** On the same IP, cold navigation directly to `nid.naver.com` was slow in both ZeroProxy and native Chrome, whereas navigating to `nid` after visiting `www.naver.com` or `pay.naver.com` was fast. This overturned the IP-only explanation and pointed to session continuity (cookies and `Referer` chain), though the individual causal weights of cookies versus `Referer` were not isolated.
- **Path and refutation:** Although [runtime-prelude.js:1659](../../web/runtime-prelude.js#L1659) cleared `document.referrer` at the time, the Service Worker handled HTTP `Referer` separately and the cookie jar preserved cookies acquired on `www`. Because the NAVER Pay shortcut navigated in `_self`, the hypothesis that `_blank` tab separation caused the delay was refuted; typing `nid.naver.com` directly into the launcher explained the cold-navigation difference.
- **Historical proposals and scope:** Proposals for parent-origin silent GET pre-warming and multi-tab cookie sharing (PHASE2 E1/D7) were unverified design notes referencing `ZP_COOKIE_SET` and `fetchThroughRuntime` in [web/sw.js](../../web/sw.js). This finding applies specifically to **cold navigation latency on `nid.naver.com`** and neither explains nor refutes the July GREASE tarpit. Earlier side claims that Phase 5.7 achieved full wire equivalence with Chrome were retracted by Phase 5.8 and July inspections.

## 2026-06-02: SUPERSEDED (attributing `nid` slow-lane solely to IP reputation)

- **Retired conclusion:** Based solely on observing that native Chrome was also slow on cold `nid.naver.com` loads while `www` and Wikipedia were fast, this entry inferred IP reputation, geolocation graylisting, or behavioral correlation and declared wire investigation complete. That conclusion was superseded by the session-continuity and wire-inspection findings above.
- **Historical implementation record:** Added `PADDING_BODY_LEN` and `random_bytes(n)` in `third_party-rustls-fork/src/ja3.rs` and padding/ECH handling in `msgs/macros.rs::encode_one`. `apply_chrome_ja3_shape` inserted padding immediately before trailing GREASE and used rustls's forced append path for ECH. **Including ECH in the contiguous extension list as well caused duplicate emission and was forbidden.** ECH emission was later removed and padding conditions were revised in Phase 5.8.
- **Evidence and status:** Historical commits `5eff860..064bffc`, `cmd/fp-probe/main.go`, `internal/fpcapture/`, and `web/sw.js::captureBrowserFingerprint`. Claims of full wire equivalence from inspection sites rested on partial hash checks and were superseded by later findings. Comparisons must separate cold vs. warm sessions, actual wire fields, TLS, HTTP headers, body framing, and DOM rendering stages.

## <a id="tls-legacy-suite-retry-2026-10-27"></a>A server that prefers a legacy cipher suite could not be reached: DCInside (2026-10-27) {#tls-legacy-suite-retry-2026-10-27}

- **Category:** `transport / TLS` (found surveying Korean sites; generic)
- **Symptom:** `www.dcinside.com` showed "Could not reach target" through the proxy and loaded in Chrome and curl. The service worker's own record said what failed: `tx:tls-err host=www.dcinside.com err=tls: process: peer misbehaved: SelectedUnofferedCipherSuite`, 15 to 40 ms after the connection opened (the page's error code read `TARGET_CONNECT_FAILED`). A Node TLS probe (`.lean-ctx/tls-probe.js`, not committed): TLS 1.2 only; offered Node's default list it chose `ECDHE-RSA-AES256-SHA` (CBC); offered one suite at a time it also accepts `ECDHE-RSA-AES128-GCM-SHA256`, `ECDHE-RSA-AES256-GCM-SHA384`, `AES128-GCM-SHA256`, and refuses ChaCha20.
- **Cause:** the browser-shaped ClientHello lists Chrome's legacy suites (`0xC013`, `0xC014`, `0x9C`, `0x9D`, `0x2F`, `0x35`) as decoys, for the shape of the hello; the TLS stack implements none of them. The comment at the place assumed that a modern server picks a TLS 1.3 or ECDHE-GCM suite. A server that follows its own preference order and has a CBC suite first picks that one, and rustls aborts the handshake. Chrome implements CBC, so it connects. The ERRATA row about decoy suites said "nothing else on the measured sites was affected"; this is a mainstream site.
- **Fix.** `ClientConfig::advertise_unimplemented_suites` (third_party-rustls-fork, default true: the previous behaviour). With false, `client::hs` keeps only the captured suites the provider implements, in their captured order (the GREASE suite is still added). The kernel (`transport/tls.rs`, `transport/fetch.rs`): a handshake that fails with `PeerMisbehaved::SelectedUnofferedCipherSuite` (carried as a typed `TlsProcessError`, so the match is on the error, not its text) is made again once, on a new stream from the dialer, with the plain hello; the host is remembered (`PLAIN_SUITE_HOSTS`) so its next connections start plain. Every other host keeps the browser-shaped hello unchanged (the Chrome persona matters for challenges); the fallback hello differs from it only in the suite list.
- **Measured after:** DCInside 1 589 against 1 583 elements natively, 46 images each, no page error. The trace of a first load: `tx:tls-retry host=www.dcinside.com reason=legacy-suite …` then `tx:tls-ok`; later connections to the host show no retry. `gall.dcinside.com` accepted the shaped hello (no retry there).
- **Closed by:** crates/zp-kernel-bundle/tests/client_hello.rs `the_browser_shaped_hello_lists_the_legacy_suites_and_the_plain_one_does_not` (fails with the filter off: "the plain hello still lists 0xc013") and `a_server_that_picks_a_legacy_suite_fails_with_the_error_the_retry_keys_on` (a hand-made ServerHello that picks a legacy suite gives exactly that error, one the plain hello offered does not). The retry itself lives in the wasm-only kernel and was measured on the real site, not pinned by an automated test (a target with a CBC preference and a chain the kernel trusts has no fixture).
- **Still unreachable:** a server that offers only CBC or static-RSA suites (`token.rubiconproject.com`): ERRATA.
