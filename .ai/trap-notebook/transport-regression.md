# Transport Regressions

Security regression history across the WASM kernel, relay, and target transport paths. Historical paths and verification gaps listed here are not a current implementation checklist.
Security invariant: client WASM owns TLS for HTTPS targets while Go operates strictly as a byte-pipe. Never pass target HTTP headers, cookies, or bodies to the server in a plaintext envelope.

## 2026-06-01: Cutover that replaced client-TLS with server-TLS {#client-tls-cutover}

- Cause: The Rust migration in commit `291db00` sent URL, method, headers, and body from `kernel_fetch` to `/zp/relay` as JSON. `http.Transport`, cookie jar, and `followRedirects` in `cmd/zeroproxy-server/relay.go` terminated TLS on the server, exposing all plaintext to the Go host. Build and render checks did not catch the regression.
- Historical fix (Step 14): Restored the WebSocket, SOCKS5, client TLS, and HTTP stack under `crates/zp-bundle/src/kernel/transport/` (`ws_stream.rs`, `socks5.rs`, `tls.rs`, `http1.rs`, `fetch.rs`). Updated `kernel_fetch` to call this transport stack and removed JSON-envelope `relay_fetch*`, `relay_round_trip`, `RelayRequest/Head`, and the legacy mux.
- Server: Removed `relay.go`, `/zp/relay`, `/zp/relay-mux`, and `/zp/ws-bridge` that owned target HTTP/TLS, switching to the TCP+SOCKS5 byte-pipe at `/zp/ws-tcp`. Regardless of subsequent crate reorganization, any regression that moves TLS ownership back to the server is forbidden.
- Historical status: Recorded HTTP/HTTPS client-TLS as restored. Unwired target WebSocket stubs, H2, yamux, and Tor auth were **gaps at that point in time**, not a statement of current unimplemented features. The kernel now lives in `crates/zp-kernel-bundle`; see the [refactoring plan](../design/website-compat-refactor.md) for current architecture and acceptance criteria.
- Verification gap: Proposed checks at the time (server route absence checks, legacy identifier greps, and packet captures) lacked execution evidence. Verify the actual `kernel_fetch` transport boundary and HTTPS wire bytes rather than relying on identifier absence alone. No new runtime verification was executed during this documentation pass.
- Evidence: commit `291db00` and the Step 14 recovery record. References to deleted `ARCHITECTURE.md` invariants and PHASE2 E1 are historical context rather than proof of current file existence.


## 2026-09-29: WebTransport gateway could not reach any target {#wt-gateway-datapath}

- **Symptom:** D4 was marked "LANDED end-to-end", but existing tests only checked 400/501 argument validation responses. Adding an end-to-end client, gateway, and real echo target datapath test exposed two stacked failures.
- **Cause 1:** The gateway dialed targets with a QUIC configuration lacking `EnableDatagrams`. `webtransport-go` rejects **every** dial with "DATAGRAM support required", causing the gateway to close sessions immediately upon acceptance.
- **Cause 2:** The bidirectional stream bridge closed both directions as soon as the first direction finished. A client that sent FIN after its request received EOF before the target response arrived (producing an empty echo). Stream halves must close independently per direction: each direction closes only its own write side (`relayHalf`) and propagates stream resets on error.
- **Residual (browser segment, resolved 2026-09-30: [browser segment](#wt-browser-segment)):** (1) Self-signed development certificates had a 30-day validity period, whereas browser `serverCertificateHashes` pinning accepts at most 14 days, preventing browsers from connecting in dev mode. (2) No plumbing existed to pass the gateway certificate hash to the page. (3) `serverCertificateHashes` supplied by the page for the **target** were passed directly to the gateway connection instead of being verified by the gateway against the target.
- **Residual (operational risk, resolved 2026-09-30: Origin restricted to public hosts, private targets allowed only with `-socks internal`):** The gateway lacked origin and authentication checks and dialed private IPs. When `AllowedTargetOrigins` was empty (the default), anyone able to reach the UDP port had an open relay and an SSRF path into the operator LAN.
- **Verification:** `TestGatewayBridgesToRealTarget` (bidirectional stream echo and datagram echo; both failed prior to the fix).


## 2026-09-30: Browser segment of the WebTransport gateway (five stacked failures visible only in a real browser) {#wt-browser-segment}

- **Symptom:** Even after the Go datapath test passed, page and worker `WebTransport` instances could not reach the gateway. Fixing each layer uncovered the next.
- **Cause 1 (CSP):** Proxied document `connect-src` directives omitted the gateway origin (on a separate port), blocking every packet with "Refused to connect". Workers use **their own bootstrap response CSP** rather than the page CSP and required a matching fix. Document headers, `<meta>` CSP rewrites, and worker bootstrap responses now share a single `proxiedCSP` helper.
- **Cause 2 (Origin):** Default `CheckOrigin` in `webtransport-go` requires the `Origin` host to match the gateway `Host` header exactly, rejecting every proxied page on a different port despite a comment claiming the default allowed all origins. The gateway now accepts its configured public hostnames regardless of port (configurable via `-wt-page-hosts`).
- **Cause 3 (Certificate):** The development self-signed certificate was a 30-day CA certificate. Because browser `serverCertificateHashes` pinning requires leaf certificates valid for at most 14 days, dev mode now generates a 13-day leaf certificate.
- **Cause 4 (Hash plumbing):** No path existed to deliver the gateway certificate hash to the page; it is now plumbed through `/zp/api/config`, Service Worker boot, and the membrane wrapper (`wtgh` query parameter on worker bootstrap).
- **Cause 5 (Target pinning):** `serverCertificateHashes` passed by the page for the **target** were previously applied to the gateway connection. The wrapper now forwards target hashes via `certhash`/`pinned` query parameters so the gateway enforces browser pinning rules against the target (matching hash, validity `<= 14` days, no chain/hostname check, and empty hash list rejection), sharing `ZP.webTransportGatewayRequest` across page and worker realms.
- **Additional fix (SW config eviction):** The Service Worker previously fetched `/zp/api/config` only during `activate`. When the browser restarted an idle Service Worker, globals reset to defaults without re-running `activate`, leaving `wtGateway` and `rtcGateway` empty. The Service Worker now refreshes config on document navigation with a 10-second TTL and bounded timeout.
- **Operational boundary (architectural exception):** Because QUIC cannot traverse TCP SOCKS5/Tor and WebTransport relaying terminates sessions at the gateway, targets see the server IP and the gateway sees stream plaintext. The server logs a startup warning whenever `-socks` is not `internal`. Private and loopback targets are permitted only under `-socks internal` (matching HTTP reachability) and dialed by verified IP to prevent DNS rebinding. Unreachable targets reject `ready` with a CONNECT failure matching native browser behavior.
- **Lesson:** Go test clients have no `Origin`, no CSP, and no browser certificate pinning policy. End-to-end verification of browser APIs requires a real browser.
- **Verification:** `test/e2e/wt-gateway.test.js` (page and worker match native across connection, bidi streams, datagrams, and bad-pin rejection, plus gateway log verification of pinned dials), 8 `wtproxy` Go tests, and 2 `prelude-units` tests.


## 2026-09-30: D5 WebRTC (replaced direct peer-leaking bridge with relay-only TURN enforcement) {#rtc-relay-only}

- **Measurement:** Proxied page A and native peer B opened a data channel using the target's own signaling. Enabling D5 (`-rtc-enable -rtc-public-url`) opened the channel, but peer B selected a **host/host** candidate pair, connecting directly to the user without traversing the gateway (zero sessions in gateway logs). The default disabled state was a stub and did not leak.
- **Cause:** The page wrapper passed `createOffer()` and `icecandidate` events **directly from the native connection** to page code. The page sent its own SDP and host candidates to the remote peer while the gateway answer collided on the same native connection. The target-side `PeerConnection` in the pion bridge was **never negotiated** (no code emitted offers or candidates, left behind an "once adapter attaches" comment), and `on*` handlers such as `pc.ondatachannel` were set on the wrapper object and never fired.
- **Broken TURN auth:** The config endpoint issued TURN-REST credentials (`<expiry>:<label>`), but the server used `NewLongTermAuthHandler`, which parsed the entire username as an integer and rejected every issued credential with "Invalid time-windowed username". Fixed by switching to `LongTermTURNRESTAuthHandler`.
- **Replacement:** The page now constructs a **real native** `RTCPeerConnection` via `Reflect.construct` (preserving prototype, events, and subclassing) while enforcing ICE configuration through `ZP.relayOnlyRTCConfiguration` in both the constructor and `setConfiguration`: `iceServers` set to server-issued TURN credentials and `iceTransportPolicy: 'relay'`. The browser gathers only relay candidates so zero packets leave the user IP directly, and end-to-end DTLS/SRTP ensures **the relay sees only ciphertext** (preserving the byte-pipe invariant unlike the WebTransport gateway). Falls back to a stub if TURN credentials are absent. Removed the pion bridge, SDP munging, and `-rtc-public-url`/`-rtc-allowed-ips` (now ignored with a warning).
- **Operational boundary:** TURN sends UDP directly. `CreatePermission` for non-public peers (`netguard.IsNonPublic`) is allowed only when `-socks internal` is set (matching the WebTransport gateway rule) and logs a startup warning otherwise. Because Chromium **ignores loopback TURN servers**, `-rtc-turn-addr` must be a routable address.
- **Test trap:** Headless Chromium advertises mDNS (`*.local`) host candidates, giving a relay-only peer no IP address for `CreatePermission`. Because real remote peers advertise `srflx` or `relay` candidates, the E2E test passes `--disable-features=WebRtcHideLocalIpsWithMdns`.
- **Verification:** `test/e2e/rtc-relay.test.js` (native uses `host/host`, proxied gathers only `relay` candidates, and peer B selects a `relay` remote candidate), `TestTURNServerAcceptsItsOwnCredentials` (confirmed failure before fix), and `prelude-units`.

## Subsequent Transport Corrections

- [2026-07-28 lost wakeup](LOG.md#2026-07-28-2): The earlier anti-bot narrative claiming NAVER withheld `END_STREAM`/deflate termination was refuted by direct H2 comparison and yamux driver investigation. Do not attribute similar latency symptoms to anti-bot withholding without transport-level proof.
- [WASM timer/cancel](LOG.md#2026-06-16-2), [h2 reset/Instant trap](LOG.md#2026-06-19-1): Target runtime correctness requires testing cancellation and error paths alongside normal responses. Do not reintroduce past cancellation races when adding timer futures.
- [Bodiless Response](LOG.md#2026-07-30-10), [H1 deadline](sw-integration.md#transport-deadline-measurement): Distinguish framing, `HEAD`/204/304 responses, and header wait deadlines from body stream lifetimes. This historical note does not claim full CI passage or complete stream cancellation coverage.
